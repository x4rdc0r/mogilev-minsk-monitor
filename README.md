# Мониторинг мест: Могилёв → Минск (3 сайта)

Скрипт проверяет свободные места на маршрутках Могилёв → Минск на заданную дату
в заданном окне времени и присылает уведомление в Telegram, когда место
освобождается (отказ, снятие брони и т.п.).

Отслеживаются три источника:

| Источник | Как получаем данные |
|---|---|
| `mogilevminsk.by` | JSON-API платформы Transporter: `POST /timetable/trips/` |
| `avto-slava.by` | та же платформа и тот же API, другая база перевозчика |
| `atlasbus.by` | Next.js: рейсы на дату лежат в `__NEXT_DATA__` страницы маршрута с `?date=` |

Текущая настройка: **08.11.2026 (вс), окно 16:30–20:00, Могилёв → Минск**.

## Как это работает

### mogilevminsk.by и avto-slava.by

Оба сайта — Angular-приложение на платформе Transporter, данные берут из открытого
JSON-эндпоинта (без авторизации и CSRF):

```
POST https://<сайт>/timetable/trips/
Content-Type: multipart/form-data

date=2026-11-08&from_city=2&dest_city=1
```

Города: `2` = Могилёв, `1` = Минск. Ответ содержит рейсы с полями
`departure_time`, `free_seats`, `all_seats`, `route_id`.

### atlasbus.by

Next.js-агрегатор: сервер отдаёт готовую страницу маршрута вместе с данными
рейсов в `__NEXT_DATA__`. Достаточно запросить страницу с датой:

```
GET https://atlasbus.by/Маршруты/Могилёв/Минск?date=2026-11-08
```

и разобрать `props.initialState.searchRides.rides` → `departure`, `freeSeats`,
`carrier`, `price`.

### Особенности данных

- `free_seats` на Transporter-сайтах отдаётся **с потолком 2**: `2` означает
  «два и более». Ноль и отрицательные значения — мест нет.
- На atlasbus число мест настоящее (может быть 5, 10 и т.д.).
- Расписание публикуется на ~10–14 дней вперёд, для 08.11 рейсы уже есть.

Монитор только уведомляет. Бронирование — вручную на сайте (форма брони,
на atlasbus может потребоваться SMS-код) или по телефонам 788-55-33, 788-66-33.

## Локальный запуск

Нужен только Python 3.9+ (внешних зависимостей нет).

```powershell
# посмотреть текущую доступность по всем источникам
python monitor.py --show

# проверка без отправки в Telegram
python monitor.py --dry-run

# отправить тестовое сообщение в Telegram (проверка токена и chat_id)
python monitor.py --test

# обычная проверка (+ уведомление, нужен TELEGRAM_BOT_TOKEN)
$env:TELEGRAM_BOT_TOKEN="123456:ABC..."
python monitor.py
```

## Telegram-бот

1. В Telegram открыть [@BotFather](https://t.me/BotFather) → `/newbot` →
   получить токен вида `123456789:AA...`.
2. Написать своему боту любое сообщение (`/start`) — это нужно, чтобы
   скрипт смог определить `chat_id` (либо задайте `TELEGRAM_CHAT_ID` вручную).

Удобнее держать токен локально в файле `.env.local` (он в `.gitignore`
и не попадёт в репозиторий):

```
TELEGRAM_BOT_TOKEN=123456789:AA...
```

Скрипт сам подхватит его при запуске.

## Запуск в GitHub Actions (24/7, бесплатно)

```powershell
# 1. Авторизоваться в GitHub
gh auth login

# 2. Создать репозиторий и запушить код
#    публичный — бесплатные минуты Actions без лимита; приватный тоже подойдёт,
#    но тогда лучше поставить cron раз в 10 минут (2000 бесплатных минут/мес)
git init
git add .
git commit -m "seat monitor"
gh repo create mogilev-minsk-monitor --public --source . --push

# 3. Добавить секреты
gh secret set TELEGRAM_BOT_TOKEN --body "123456:ABC..."
# необязательно, если бот уже получал сообщения от вас:
gh secret set TELEGRAM_CHAT_ID --body "123456789"

# 4. Запустить вручную и посмотреть результат
gh workflow run monitor.yml
gh run watch
```

Workflow `Seat monitor` запускается по расписанию каждые 5 минут.
Расписание задаётся в `.github/workflows/monitor.yml` (cron в UTC).

Если workflow падает (все сайты недоступны, изменился API), GitHub пришлёт
письмо — молчаливого отказа не будет. Если недоступен только один сайт,
остальные продолжают работать, а упавший не сбрасывает своё состояние.

## Быстрый локальный вариант (пока ПК включён)

GitHub cron даёт интервал ~5 минут и иногда задерживается. Если нужна реакция
за секунды, запустите тот же скрипт локально — он опрашивает каждые 45 секунд
и пишет состояние в отдельный файл `state.local.json`:

```powershell
$env:TELEGRAM_BOT_TOKEN="123456:ABC..."
.\run_local.ps1              # опрос каждые 45 с
.\run_local.ps1 -IntervalSeconds 30
```

Оба варианта можно держать включёнными одновременно — они не мешают друг другу
(разные файлы состояния), просто уведомления могут прийти дважды.

## Настройка

Параметры задаются переменными окружения (значения по умолчанию — в скобках):

| Переменная | Значение |
|---|---|
| `TARGET_DATE` | дата поездки, `YYYY-MM-DD` (`2026-11-08`) |
| `WINDOW_START` | начало окна времени (`16:30`) |
| `WINDOW_END` | конец окна времени (`20:00`) |
| `MIN_FREE_SEATS` | минимально нужное число мест (`1`) |
| `SOURCES` | список id источников через запятую (по умолчанию все) |
| `TELEGRAM_BOT_TOKEN` | токен бота |
| `TELEGRAM_CHAT_ID` | id чата (если не задан — определяется автоматически) |
| `STATE_FILE` | файл состояния (`state.json`) |

В GitHub Actions эти переменные задаются в блоке `env:` шага «Проверка мест».

## Файлы

- `monitor.py` — весь мониторинг (stdlib, ретраи, три источника, антиспам).
- `state.json` — что уже было доступно по каждому источнику: чтобы не присылать
  одно и то же каждые 5 минут, workflow коммитит файл обратно в репозиторий.
- `.github/workflows/monitor.yml` — запуск по cron + ручной запуск
  (в том числе тестовое сообщение в Telegram).
- `run_local.ps1` — локальный цикл с интервалом 45 с (опционально).
- `.gitignore`
